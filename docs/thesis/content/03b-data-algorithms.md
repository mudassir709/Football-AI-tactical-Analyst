## Data design

### Database

The relational data is small and simple, so the database has two tables (Figure 3.6). PostgreSQL was chosen for its reliability, its native JSON column type (used for the match summary) and its first-class support in Prisma. The schema is defined in `backend/prisma/schema.prisma`; Prisma generates a fully typed client from it and turns every schema change into an SQL migration file (`backend/prisma/migrations/`), which is applied automatically when the backend container starts.

The large analysis output is deliberately **not** stored in the database: a 30-second clip produces a results file of about 0.55 MB, which is served directly from disk, while the database keeps only the small summary needed for lists.

### Match lifecycle

The `status` column follows the state machine in Figure 3.7. The API sets QUEUED when the job is created; all other transitions are driven by queue events. A failed attempt goes back to QUEUED while a retry is pending, so the user never sees FAILED for an error that is about to be retried.

![States of a match](figures/status.png){w=15.5}

### File storage

Files live in the storage folder shared by the API and the worker: `videos/` holds the uploads (stored under a random UUID name with the original extension) and the playback copies (`<matchId>_web.mp4`), and `results/` holds the results files (`<matchId>.json`). The API never trusts a path from outside: `absolutePath()` resolves every stored relative path and refuses any result that escapes the storage folder, and the worker performs the same check before opening a file.

### Queue messages

A job in the `match-analysis` queue carries `{matchId, videoPath, mode}`. While working, the worker calls `updateProgress({percent, stage})`. On success it returns `{resultPath, playbackPath, summary}`; on failure the exception message becomes the job's failure reason. Jobs are configured with two attempts and a fixed 10-second back-off, and the last 500 completed and failed jobs are kept for monitoring.

### The results file

The results file is the contract between the worker and the dashboard. It is a single JSON document; its main fields are listed in Table 3.8. The per-frame data uses compact arrays instead of objects, which halves the size of the frame data (0.45 MB instead of 0.95 MB for a 30-second clip); a `legend` field documents the array layouts inside the file itself.

## The analysis pipeline

This section describes the computer vision and analysis algorithms, which form the technically most demanding part of the project. The pipeline is implemented in `worker/src/` and orchestrated by `run_analysis()` in `pipeline.py` (Figure 3.8). Every stage is a separate module with a small, testable interface; stages exchange pandas DataFrames in which each row is one detection of one object in one frame.

![The stages of the analysis pipeline with their share of the progress bar](figures/pipeline.png){w=11}

### Video input and playback copy

Videos are read frame by frame with a generator (`iter_frame_batches`), so even a full match is never held in memory: only a batch of four frames exists at any time. The analysis mode determines the **stride**: Standard mode analyses every 2nd frame, Quick mode every 5th. The time of frame *i* is *i / fps*, so all later stages work with real timestamps regardless of the stride.

Before the analysis, the worker re-encodes the upload into a browser-compatible copy (`transcode.py`, using PyAV and libx264 [28]). Uploads can use codecs that browsers cannot play (for example HEVC or MPEG-4 Part 2), so this step guarantees playback. Two details matter for the overlays: every input frame becomes exactly one output frame at a constant frame rate, so frame *i* of the copy is frame *i* of the original and the overlay timing stays exact; and the file is written with the "faststart" flag, which moves the index to the front so playback can start before the whole file is downloaded. This step runs first because it also fails fast on unreadable files.

### Object detection

Detection uses YOLOv8 [1], a single-stage convolutional detector that predicts bounding boxes and class scores for the whole image in one forward pass. The project uses the YOLOv8x weights trained by Roboflow on broadcast football footage [4] with the classes ball, goalkeeper, player and referee. `FootballDetector` wraps the model:

- frames are processed in batches of four for better hardware utilisation;
- the model's labels are mapped onto the pipeline's canonical class IDs through a table of aliases, so a generic COCO model [30] can serve as a fallback ("person" → player, "sports ball" → ball);
- YOLO filters with the lowest threshold of all classes, and stricter **per-class confidence thresholds** are applied afterwards (Table 3.9). The ball is tiny (often 5–10 pixels at 1280-pixel resolution) and frequently blurred, so it gets a lower threshold; false positives are removed later by keeping only one ball per frame.

Table: Detection parameters {widths=40,20,40}
| Parameter | Value | Reason |
|---|---|---|
| Input resolution | 1280 px (Quick: 960 px) | The model was trained at 1280 px; lower values miss the ball. |
| Confidence, ball | 0.15 | Small, blurred object. |
| Confidence, players, goalkeepers, referees | 0.30 | Reliable large objects. |
| Non-maximum suppression IoU | 0.5 | Merges overlapping boxes of the same object. |

### Multi-object tracking

Detections in individual frames carry no identity. ByteTrack [2] links them into tracks with stable IDs. Each track's box is predicted into the next frame with a Kalman filter (constant-velocity motion model) and matched to new detections by intersection over union (IoU). ByteTrack's key idea is a two-stage association: first, high-confidence detections are matched to the predicted tracks; then the remaining tracks are matched to the **low-confidence** detections, which other trackers discard. Low-confidence detections are typically occluded players, so keeping them in the second stage greatly reduces identity switches in crowded situations such as set pieces.

`FootballTracker` (in `tracker.py`) applies ByteTrack only to people. Before tracking, overlapping detections are merged class-agnostically, because the detector sometimes labels the same person both "player" and "goalkeeper". Tracks are confirmed after two consecutive frames and kept for 50 frames (2 seconds at 25 fps) after they are lost, so a briefly occluded player keeps their ID. The tracker receives the real timestamp of each frame, which keeps its motion prediction correct when frames are skipped by the stride.

The ball is handled separately: there is only one ball, it moves too fast and too erratically for IoU matching, and it is missed in many frames. The tracker therefore keeps only the most confident ball detection per frame; gaps are filled later (Section 3.5.6).

The output is the *tracks table*: one row per person or ball per analysed frame with frame index, timestamp, tracker ID, class, confidence, box corners and the **foot point**, the bottom centre of the box, where the player touches the grass.

### Mapping the image onto the pitch: homography

To measure distances in metres, every foot point must be converted from image pixels to pitch coordinates. The pitch is a plane, and the mapping between a plane in the world and its image under a pinhole camera is a **homography** [5]: a 3 × 3 matrix *H*, defined up to scale, that maps homogeneous image coordinates to homogeneous pitch coordinates:

$$ (X, Y, W)ᵀ = H · (x, y, 1)ᵀ,    pitch point = (X / W, Y / W) $$

*H* has eight degrees of freedom, so four point correspondences determine it; with more points it is estimated in a least-squares sense with the direct linear transform (DLT). The correspondences come from a second YOLOv8 model, a pose model that locates up to 32 **pitch landmarks** in the image: the corners of the pitch and of both penalty and goal areas, the penalty spots, the ends of the halfway line and points of the centre circle (Figure 3.9). Their real positions on a FIFA-standard 105 × 68 m pitch are known (`PitchDimensions.keypoints`).

![The 32 pitch landmarks and their positions in pitch coordinates](figures/pitch_keypoints.png){w=13}

The broadcast camera pans and zooms continuously, so a separate homography is estimated for every analysed frame (`HomographyEstimator.update`):

1. Keypoints with a confidence below 0.5 are discarded; at least four must remain.
2. **Degeneracy check**: if the pitch positions of the remaining keypoints span a convex hull of less than 50 m², they are nearly collinear (for example only points on the halfway line are visible) and give an unstable result, so the frame is rejected.
3. The homography is fitted with **RANSAC** [6] (`cv2.findHomography`): random minimal subsets of four correspondences are used to fit candidate matrices, each candidate is scored by the number of keypoints it projects to within 1 metre of their true position, and the best model is refitted on all its inliers. A single wrongly located keypoint therefore cannot spoil the result. At least four inliers are required.
4. The mean distance between the projected inliers and their true positions, the **reprojection error** in metres, is stored as a quality measure.
5. If a frame yields no valid homography, the previous one is reused for at most 10 processed frames; beyond that the camera has probably moved too far and the frame is left without pitch coordinates.

Because the camera moves smoothly, running the pitch model on every analysed frame is unnecessary. In Standard mode it runs on every 3rd analysed frame (every 6th video frame), in Quick mode on every 2nd. `project_tracks` then assigns each tracked frame the homography of the **nearest** frame that has one (within one pitch stride) with a nearest-neighbour `merge_asof` join, and projects all foot points in a single vectorised NumPy operation (Listing 3.3). This halves the cost of the stage with no measurable loss of accuracy.

Listing: Vectorised projection of all foot points (from worker/src/homography.py)
```
h = merged[HOMOGRAPHY_COLUMNS].to_numpy()          # one 3x3 matrix per row
x, y = merged["foot_x"].to_numpy(), merged["foot_y"].to_numpy()
w = h[:, 6] * x + h[:, 7] * y + h[:, 8]
merged["pitch_x"] = (h[:, 0] * x + h[:, 1] * y + h[:, 2]) / w
merged["pitch_y"] = (h[:, 3] * x + h[:, 4] * y + h[:, 5]) / w
```

For the dashboard, the worker also exports the **inverse** matrix (pitch → image) of every frame. It allows the browser to draw anything defined on the pitch, such as paths and heatmaps, back onto the video frame (Section 3.8.4). Homographies are only defined up to scale; the exported matrix is normalised to unit Frobenius norm, with the sign chosen so that the pitch centre has a positive depth *W*. An earlier version divided by the last matrix element instead, which is close to zero for some camera angles; Section 3.11.7 describes how testing revealed this.

### Team assignment

Players are assigned to teams by the colour of their shirts (`clustering.py`). The difficulty is that a crop of a player also contains grass, and the grass colour varies with mowing stripes, shadows and floodlights. The algorithm works per track rather than per detection, which averages out occlusion, motion blur and lighting changes:

1. **Roles.** The detector's class label flickers between frames, so each track gets one role: the most frequent class, except that a track becomes a goalkeeper if at least 25 % of its detections say so (the detector often calls a goalkeeper "player", but rarely the reverse).
2. **Sampling.** For every player and goalkeeper track, up to 10 detections evenly spread over the track's lifetime are sampled. The video is decoded once, sequentially, and only the frames containing samples are cropped.
3. **Torso colour.** From each box, the torso region (15–50 % of the height, 25–75 % of the width) is taken, skipping the head and the shorts. The pixels are converted to the CIE Lab colour space [9], in which Euclidean distances approximate perceived colour differences.
4. **Local grass removal.** The grass colour is measured in a ring around the player's box (the median Lab colour of the ring). Torso pixels within a Lab distance of 22 from this local grass colour are discarded, with the lightness component weighted by 0.5 so that lighter and darker mowing stripes still count as grass. The shirt colour is the median of the remaining pixels.
5. **Clustering.** The median colour over a track's samples is its shirt colour. K-Means [8] with *k* = 2 (10 initialisations, fixed seed for reproducibility) splits the player tracks into two teams. The numbering is made deterministic: the team with the lighter cluster centre becomes Team A.
6. **Goalkeepers** wear a kit different from their team, so they are assigned by position instead: to the team whose per-frame centroid is on average closest to them.

For every track, the share of its individual crops that vote for its team is stored as an **agreement** score, a measure of how consistent the assignment is. Measuring the grass locally rather than with a fixed "green" range was a correction made during testing: a fixed range also removed green and lime-coloured shirts (Section 3.11.7).

### Smoothing and ball interpolation

Box corners jitter by a few pixels from frame to frame, which after projection becomes noise of tens of centimetres and would inflate the measured running distances. Each person's pitch trajectory is therefore smoothed with a centred rolling mean over one second (`smooth_positions`); the raw values are kept alongside. The ball is not smoothed because it changes direction abruptly. Instead, gaps in the ball trajectory of up to one second are filled by linear interpolation between the last and next detection (`interpolate_ball`); interpolated rows are marked so that they are not counted as detections. Longer gaps stay empty, because the ball has probably left the camera's view.

### Formation detection

A formation describes the arrangement of a team's ten outfield players in lines from defence to attack, such as 4-4-2. Players constantly move, so the formation is not visible in a single frame. `detect_formations` therefore works on time windows of 5 seconds:

1. **Defending side.** The goal each team defends is determined from its goalkeeper's average position, or, without a goalkeeper, from the team's average position (defenders stay goal-side of attackers).
2. **Attacking frame.** Positions of the team that defends the right goal are rotated by 180°, so that every team attacks in the direction of increasing *depth*.
3. **Role centroids.** For each window, every outfield player's positions are averaged. Only players visible in at least 50 % of the window's frames are used, at most the 10 most visible ones. A window with fewer than 8 such players is left unclassified, since the broadcast camera rarely shows the whole team.
4. **Normalisation.** The centroids are scaled to the unit square (min-max per axis), so that the *shape* of the team is compared, independent of where on the pitch it stands and how stretched it is.
5. **Matching.** Each of nine candidate formations is described by a template of ten slots (Figure 3.10): the lines are evenly spaced in depth from 0 (defence) to 1 (attack), and the players of a line are spread evenly across the width (a line of two takes the positions 0.3 and 0.7, a line of one the centre). The cost of a template is the mean distance between players and slots under the **optimal one-to-one assignment**, which is found with the Hungarian algorithm [7] (`scipy.optimize.linear_sum_assignment`). With fewer than ten players, the rectangular assignment automatically picks the best subset of slots.
6. **Hysteresis.** The template with the lowest cost is the best match, and the second-lowest is the runner-up. Neighbouring templates often differ by very little (Section 3.11.4), and a naive classifier would flicker between them. The reported formation therefore only changes when the new best template is better than the current one by more than 0.03. The difference between runner-up and best match is stored as a confidence margin.

![The nine formation templates](figures/formation_templates.png){w=11}

Figure 3.11 shows one real window from the first test clip: the Hungarian assignment of Team B's ten average positions to the 5-3-2 template (cost 0.151) and to the runner-up 5-4-1 (cost 0.176). The five-player back line fits both, but the two advanced players match two strikers better than one.

![Formation matching for one window of clip 1: best match and runner-up](figures/formation_matching.png){w=15.5}

The assignment is solved optimally rather than greedily because a greedy nearest-slot rule can give two players the same slot or force a later player into a distant one, which distorts the cost. With ten players the Hungarian algorithm's O(n³) running time is negligible: nine templates for each window of a 30-second clip are matched in milliseconds.

Listing: Template matching with the Hungarian algorithm (from worker/src/clustering.py)
```
def match_formation(positions, formations=config.FORMATIONS):
    observed = _normalise_shape(positions)
    costs = {}
    for formation in formations:
        template = formation_template(formation)
        distances = np.linalg.norm(observed[:, None, :] - template[None, :, :], axis=2)
        rows, cols = linear_sum_assignment(distances)
        costs[formation] = float(distances[rows, cols].mean())
    return costs
```

### Tactical and physical metrics

`metrics.py` computes the measurements shown in the dashboard from the smoothed trajectories:

- **Team shape** (per frame and team, outfield players only): the **compactness** is the area of the convex hull of the players' positions [31], computed with Qhull through SciPy; the **width** is the extent across the pitch (range of *y*), the **depth** the extent from goal to goal (range of *x*); the **centroid** is the mean position. At least three players are needed for an area.
- **Distance and speed** (per track): the distance is the sum of the steps between consecutive positions. A step is ignored if the time between the two positions is more than three frame intervals (the track was lost in between) or if it implies a speed above 12 m/s (elite sprinters peak at about 10–11 m/s, so such a step is a tracking glitch, typically an ID jumping to another player). Time visible is the number of frames times the frame interval; the average speed is distance divided by time visible; the top speed is the largest valid step speed. Speeds are reported in km/h.
- **Heatmaps** divide the pitch into a 21 × 14 grid of cells of 5 × 4.9 m and count the share of positions falling into each cell, for each team, each player and the ball.

### Analysis modes and performance parameters

The cost of the analysis is dominated by the two neural networks. The analysis modes (Table 3.10) trade accuracy for speed through three parameters. Additionally, both models are loaded only once per worker process (`functools.cache`), not for every job.

Table: Parameters of the analysis modes {widths=34,22,22,22}
| Parameter | Standard | Quick | Effect |
|---|---|---|---|
| Stride (analyse every n-th frame) | 2 | 5 | Fewer frames, proportionally faster |
| Detection resolution | 1280 px | 960 px | Lower resolution is faster but finds fewer balls |
| Pitch model on every n-th analysed frame | 3 | 2 | Fewer homographies, shared with neighbours |
